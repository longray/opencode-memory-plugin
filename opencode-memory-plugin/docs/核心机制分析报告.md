## 一、Agent-Driven 自动化记忆机制

### 1.1 核心设计理念

**设计哲学**: "无感知记忆" - 用户无需主动保存，AI自动识别并保存重要信息

**触发模式**:

- **被动触发**: 用户通过 `@memory-automation` 显式调用
- **主动触发**: 后台监听对话，自动识别重要信息（未来实现）

### 1.2 自动化记忆 Agent 架构

**Agent 配置** (memory-automation.md):

```yaml
mode: subagent
model: anthropic/claude-haiku-4-20250514
tools: [memory_write, memory_read, memory_search, memory_search]
permissions:
  - memory_write: allow
  - memory_read: allow
  - memory_search: allow
  - memory_search: allow
  - bash: deny (安全限制)
```

**核心职责**:

1. 分析对话历史，识别有价值的信息
2. 分类信息优先级（高/中/低）
3. 去重检查（避免重复保存）
4. 自动写入到合适的记忆文件

### 1.3 信息识别模式

**高优先级信息** (Always Save):

- 用户偏好声明: "I prefer/like/dislike..."
- 项目约定: "Always do/never do..."
- 成功模式: "This pattern worked well..."
- 重要决策: "We decided to use X because..."
- 用户反馈: "Good/bad/great/terrible"
- 经验教训: "Learned that X causes Y..."

**中优先级信息** (Save if Unique):

- 独特问题及解决方案
- 配置细节
- 任务完成记录
- 工作流改进

**低优先级信息** (Skip):

- 临时调试信息
- 一次性命令
- 已存在的重复信息
- 常规操作记录

### 1.4 识别算法

**模式匹配规则**:

```javascript

  decisions: /(decided|chose|selected) .* because/i,
  feedback: /(good|bad|great|terrible|excellent|poor)/i,
  lessons: /(learned|discovered|found out) that/i,

```

**上下文分析**:

- 检查对话历史的最近 N 条消息
- 识别关键信息的上下文
- 提取完整的语义单元（不截断句子）

### 1.5 去重机制

**三层去重策略**:

1. **语义去重** (memory_search):

2. **关键词去重** (memory_search):

## 二、记忆归并整理机制 (Memory Consolidation)

**设计哲学**: "定期维护" - 自动整理和归档记忆，保持系统健康和高效

**触发时机**:

1. **定期触发**: 每日结束时（23:00）
2. **手动触发**: 用户调用 `@memory-consolidate`
3. **自动触发**: 向量索引过期时
4. **归档触发**: 归档旧日志前

### 2.2 归并整理 Agent 架构

**Agent 配置** (memory-consolidate.md):

```yaml
mode: subagent
model: anthropic/claude-haiku-4-20250514
```

**核心职责**:

1. 审查每日记忆日志
2. 识别有价值的信息
3. 去重并合并到长期记忆
4. 归档旧日志文件
5. 重建向量索引

### 2.3 归并流程 (6步骤)

**Step 1: 列出最近日志**

**Step 2: 分析每日文件**

**高优先级** (Always Consolidate):

- 用户偏好的演变
- 成功的模式或解决方案
- 重要决策及理由
- 从错误中学到的教训
- 项目特定约定的发现
- 收到的反馈（正面/负面）

**中优先级** (Consider Consolidating):

- 成功完成的任务
- 遇到的独特问题
- 配置细节
- 工作流改进

**低优先级** (Skip):

- 临时调试笔记
- 常规操作
- 长期记忆中已有的重复信息
- 没有持久价值的一次性命令

**Step 3: 去重检查**


**应该合并的情况**:

## 三、记忆搜索机制

### 3.1 搜索架构概览

**三层搜索体系**:

1. **关键词搜索** (BM25) - 快速、精确匹配
2. **向量搜索** (Semantic) - 语义理解、模糊匹配
3. **混合搜索** (Hybrid) - 融合两者优势

**搜索流程**:

```
用户查询 → 搜索模式选择 → 执行搜索 → 结果融合 → 排序返回
```

### 3.2 关键词搜索 (BM25)

#### 3.2.1 BM25 算法原理

**核心公式**:

```
BM25(D, Q) = Σ IDF(qi) × (f(qi, D) × (k1 + 1)) / (f(qi, D) + k1 × (1 - b + b × |D| / avgdl))
```

**参数说明**:

- `k1 = 1.2`: 词频饱和参数（控制词频的影响）
- `b = 0.75`: 文档长度归一化参数
- `IDF(qi)`: 逆文档频率（衡量词的重要性）
- `f(qi, D)`: 词在文档中的频率
- `|D|`: 文档长度
- `avgdl`: 平均文档长度

#### 3.2.2 中文分词优化

**分词策略** (bm25.js):

```javascript
tokenize(text) {
  const lowerText = text.toLowerCase();
  const spaceSplit = lowerText.replace(/[^\w\u4e00-\u9fa5\s]/g, ' ').split(/\s+/);

  const tokens = [];
  for (const part of spaceSplit) {
    const hasChinese = /[\u4e00-\u9fa5]/.test(part);

    if (hasChinese) {
      // 中文：提取2字以上词组 + 单个字符
      const chineseWords = part.match(/[\u4e00-\u9fa5]{2,}/g) || [];
      const singleChars = part.match(/[\u4e00-\u9fa5]/g) || [];
      tokens.push(...chineseWords, ...singleChars);

      // 保留混合的英文部分
      const englishParts = part.match(/[a-z0-9]+/g) || [];
      tokens.push(...englishParts.filter(w => w.length > 1));
    } else {
      // 英文：直接作为token
      if (part.length > 1) tokens.push(part);
    }
  }
  return tokens;
}
```

**优化效果**:

- Recall: 0-14% → 82.5% (提升68.5%)
- MRR: 0.7033 → 0.7939 (提升12.9%)

#### 3.2.3 搜索执行

**性能特征**:

- 时间复杂度: O(N×M) N=文档数, M=查询词数
- 空间复杂度: O(N×V) V=词汇表大小
- 搜索延迟: <50ms (1000文档)

### 3.5 后端集成搜索

#### 3.5.1 Wrapper Client 架构

**HTTP客户端** (wrapper-client.js):

```javascript
class WrapperClient {
  constructor(config = {}) {
    this.baseUrl = config.backend?.url || 'http://localhost:17999';
    this.tenantId = config.backend?.tenant_id || 'default';
    this.timeout = config.backend?.timeout || 30000;
    this.maxRetries = config.backend?.max_retries || 3;
  }

  async search({ query, mode = 'hybrid', limit = 10, threshold = 0.3 }) {
    return await withRetry(
      () =>
        this.http.post('/api/v1/memories/search', {
          query,
          mode,
          limit,
          threshold,
          tenant_id: this.tenantId,
        }),
      this.maxRetries
    );
  }
}
```

#### 3.5.2 搜索模式对比

| 模式      | 技术    | 速度   | 质量     | 适用场景         |
| --------- | ------- | ------ | -------- | ---------------- |
| `keyword` | BM25    | ⚡⚡⚡ | ⭐⭐     | 精确关键词匹配   |
| `vector`  | Cosine  | ⚡⚡   | ⭐⭐⭐   | 语义相似搜索     |
| `hybrid`  | RRF融合 | ⚡⚡   | ⭐⭐⭐⭐ | 综合搜索（推荐） |

### 3.6 搜索性能优化

#### 3.6.1 索引优化

**当前状态**:

- ❌ 向量搜索无HNSW索引（全表扫描）
- ✅ BM25内存索引（快速）
- ❌ 无查询缓存

**优化方案**:

1. **HNSW索引**: 使用sqlite-vec的HNSW功能
2. **查询缓存**: LRU缓存最近查询结果
3. **批量查询**: 支持批量embedding请求

**预期提升**:

- 向量搜索: O(N) → O(log N)
- 搜索延迟: 100-200ms → 20-50ms
- 缓存命中: 延迟降低80%

### 3.7 搜索质量评估

**评估指标**:

- **Recall**: 召回率（找到相关文档的比例）
- **Precision**: 精确率（返回结果的准确性）
- **MRR**: 平均倒数排名（首个相关结果的位置）
- **NDCG**: 归一化折损累积增益

**当前性能** (基于测试):

- BM25 Recall: 82.5%
- BM25 MRR: 0.7939
- 向量搜索 Recall: ~85%
- 混合搜索 Recall: ~90%

### 4.2 当前架构限制

#### 4.2.1 自动化限制

- ❌ **无主动触发**: 需要用户手动调用 @memory-automation
- ❌ **无实时监听**: 无法实时监听对话并自动保存
- ❌ **无用户反馈**: 无法学习用户偏好和调整识别模式
- ❌ **无质量评分**: 无法评估保存的记忆质量

#### 4.2.2 性能限制

- ❌ **向量搜索无HNSW**: 全表扫描，O(N)复杂度
- ❌ **无查询缓存**: 重复查询无法利用缓存
- ❌ **同步I/O**: 大量使用同步文件操作
- ❌ **单节点架构**: 无法水平扩展

#### 4.2.3 功能限制

- ❌ **无合并历史**: 无法追踪合并操作历史
- ❌ **无回滚机制**: 无法撤销错误的合并
- ❌ **无访问统计**: 无法基于访问频率优化
- ❌ **无智能推荐**: 无法主动推荐相关记忆
