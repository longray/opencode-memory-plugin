## Context

当前 OpenCode Memory Plugin 的记忆数据分散在多个位置：

- **插件端本地**：`~/.opencode/memory/timeline/` 包含时间线格式的记忆条目
- **后端 SurrealDB**：存储 Entity 和 Atom 数据
- **后端 Meilisearch**：提供搜索索引

这些数据缺乏统一的结构化组织，导致：

1. 知识检索效率低下（需要遍历多个来源）
2. 知识关联性弱（缺乏图谱关系）
3. 知识复用困难（难以发现相关内容）

本设计旨在构建两种互补的知识图谱：

- **对话知识图谱**：从 OpenCode 会话中提取技术决策、问题解决方案等
- **代码知识图谱**：从代码分析中提取函数、类、模块关系

## Goals / Non-Goals

**Goals:**

- 建立结构化的对话知识图谱，包含技术决策、问题解决方案、代码模式等
- 建立代码知识图谱，包含函数、类、模块及调用关系
- 实现知识图谱的可检索性（支持 keyword/vector/hybrid 搜索）
- 建立知识提取的自动化流程和标准规范
- 保留核心配置文件，仅清理知识数据

**Non-Goals:**

- 不修改记忆系统的核心架构（保留 Entity-Atom 设计）
- 不删除配置文件（AGENTS.md, SOUL.md 等）
- 不实现实时自动提取（本次为一次性构建）
- 不迁移历史数据（重新构建而非迁移）

## Decisions

### 决策 1：选择性清理而非全量清空

**选择**：仅清理 `timeline/` 下的条目文件和索引文件，保留核心配置

**理由**：

- AGENTS.md, SOUL.md 等包含系统配置和身份定义，删除会导致系统行为异常
- memory-config.json 包含用户配置，不应删除
- 仅清理知识数据（timeline 条目）可以重建而不影响系统功能

**替代方案**：

- 全量清空：风险太高，可能破坏系统配置
- 保留所有数据：无法达到重建知识图谱的目标

### 决策 2：使用现有工具链（不开发新工具）

**选择**：使用 `session_list`, `session_read`, `code-analyzer`, `memory_write` 等现有工具

**理由**：

- 工具已成熟，无需额外开发
- 与现有工作流保持一致
- 可以利用工具的自动同步功能

**替代方案**：

- 开发专用提取工具：增加维护成本
- 直接操作数据库：绕过业务逻辑，风险高

### 决策 3：Entity-Atom 双层结构

**选择**：使用 Entity 作为知识容器，Atom 作为具体知识点

**理由**：

- 与现有 v3.3 Atom Architecture 保持一致
- 支持层级化组织（Chapter → Section → Note）
- 支持渐进加载（Level 0/1/2）

**Entity 类型设计**：

- `decision`：技术决策记录
- `solution`：问题解决方案
- `pattern`：代码模式
- `code_module`：代码模块分析
- `code_function`：函数分析
- `code_class`：类分析

### 决策 4：先清空后重建（非增量更新）

**选择**：清空现有数据后重新构建，而非增量更新

**理由**：

- 避免数据冲突和重复
- 确保知识图谱的一致性
- 可以重新设计知识结构

**风险**：

- 历史知识丢失 → 缓解：通过 session 工具可以重新提取

## Risks / Trade-offs

| 风险               | 影响 | 缓解措施                                               |
| ------------------ | ---- | ------------------------------------------------------ |
| 误删配置文件       | 高   | 明确白名单：仅删除 timeline/\*.md，保留根目录 .md 文件 |
| 会话数据提取不完整 | 中   | 使用 session_search 辅助筛选，人工确认关键会话         |
| 代码分析遗漏       | 中   | 使用 code-analyzer --project 全量分析，交叉验证        |
| 后端清空失败       | 中   | 先检查健康状态，失败时重试，记录错误日志               |
| 知识图谱搜索不准确 | 低   | 构建后运行验证测试，调整搜索参数                       |

**Trade-offs**：

- **完整性 vs 时效性**：选择重建而非增量，牺牲历史数据换取结构一致性
- **自动化 vs 准确性**：使用自动提取 + 人工确认，平衡效率和准确性

## Migration Plan

### Phase 1: 备份与清理（30分钟）

1. 备份核心配置文件（可选）
2. 清理插件端 timeline 数据
3. 清理后端 SurrealDB/Meilisearch
4. 验证清理完成

### Phase 2: 代码知识图谱构建（1小时）

1. 运行 code-analyzer 分析项目
2. 提取函数、类、模块信息
3. 组织为 Entity-Atom 结构
4. 使用 memory_write 保存

### Phase 3: 对话知识图谱构建（2小时）

1. 使用 session_list 获取历史会话
2. 筛选有价值的会话
3. 使用 session_read 提取内容
4. 组织为 Entity-Atom 结构
5. 使用 memory_write 保存

### Phase 4: 验证（30分钟）

1. 运行搜索测试
2. 验证知识图谱可检索
3. 测试典型查询场景
4. 生成验证报告

### Rollback Strategy

- 清理前可选备份 timeline 目录
- 后端清空可通过重新上传恢复
- 核心配置文件保留，系统功能不受影响

## Open Questions

1. **会话筛选标准**：如何自动识别有价值的会话？（需要定义信号词和规则）
2. **知识去重**：如何避免重复提取相似知识？（需要查重机制）
3. **关系建立**：如何自动建立 Entity 之间的关系？（需要关系识别规则）
4. **搜索优化**：如何调整搜索权重以获得最佳结果？（需要实验验证）
