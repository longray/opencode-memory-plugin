## Context

当前知识图谱状态：

- **实体总数**: 124个（103代码实体 + 21对话知识实体）
- **关系总数**: 69个
- **网络密度**: 0.009（偏低）
- **关系网络评分**: 65分（目标80+）
- **平均每实体关系**: 0.56个

**关键问题**:

1. **新对话知识实体孤立**: 新提取的20个decision/solution/pattern实体与代码实体缺乏关联
2. **关系类型单一**: 主要为contains关系，缺少applies_to/implements/related_to等语义关系
3. **网络连通性差**: 大量实体只有1-2个关系，形成孤岛
4. **缺乏持续监控**: 无自动化质量监控和定期优化机制

## Goals / Non-Goals

**Goals:**

- 建立新对话知识实体与相关代码实体的跨类型关系（目标50+个新关系）
- 补充15-20个新的技术决策/方案/模式实体
- 提升关系网络密度至0.02+（当前0.009）
- 提升关系网络评分至80+（当前65）
- 建立质量监控机制：每周搜索质量报告、每月关系健康度检查
- 建立持续优化流程：自动检测孤立实体、推荐关系建立

**Non-Goals:**

- 不修改现有实体内容（仅建立关系）
- 不删除已有关系
- 不修改Entity-Atom架构
- 不实现实时关系更新（本次为批量建立）

## Decisions

### 决策 1：跨类型关系建立策略

**选择**：基于关键词匹配 + 语义相似度建立对话知识→代码实体关系

**关系类型**：

- `applies_to`: decision/solution → code_module/code_class（决策应用于代码）
- `implements`: pattern → code_function（模式实现为代码）
- `related_to`: decision/solution/pattern ↔ code_entity（双向关联）
- `depends_on`: solution → decision（方案依赖于决策）

**匹配算法**：

1. 提取对话知识实体中的关键词（技术术语、模块名、类名）
2. 在代码实体中搜索匹配的关键词
3. 计算语义相似度（BM25 + vector hybrid）
4. 阈值>0.7时建立关系

**理由**：

- 关键词匹配准确率高
- 语义相似度避免误匹配
- 多种关系类型表达不同语义

**替代方案**：

- 纯人工标注：成本高，不可扩展
- 纯语义匹配：召回率高但精准度低

### 决策 2：关系权重计算

**选择**：基于匹配强度和实体重要性计算权重

**公式**：

```
weight = base(0.5) + match_strength(0.3) + entity_importance(0.2)
```

**match_strength**: 关键词匹配数 / 总关键词数
**entity_importance**: 代码实体被引用次数 / 最大引用次数

**归一化**: [0.3, 1.0]

**理由**：

- 匹配强度反映关系确定性
- 实体重要性反映关系价值
- 可解释性强

### 决策 3：质量监控机制

**选择**：三级监控：实时监控 → 每周报告 → 每月优化

**实时监控**（每次搜索后）：

- 记录查询响应时间
- 记录结果相关性评分
- 检测异常（超时、空结果）

**每周报告**（自动化）：

- 搜索质量指标（precision@K, recall, latency）
- 关系健康度（孤立实体数、平均关系数）
- 覆盖率变化（新增实体数、覆盖率%）

**每月优化**（人工审核）：

- 审核孤立实体并建立关系
- 优化低权重关系
- 补充缺失的知识实体

**理由**：

- 分层监控，资源合理分配
- 自动化+人工结合，平衡效率和质量

### 决策 4：持续优化流程

**选择**：建立标准作业程序（SOP）

**SOP-1: 孤立实体处理**

1. 每月1日自动检测孤立实体
2. 生成孤立实体报告
3. 人工审核并建立关系
4. 更新关系图谱

**SOP-2: 关系权重优化**

1. 每季度检测低权重关系（<0.5）
2. 分析原因（匹配错误？实体变更？）
3. 重新计算权重或删除关系
4. 更新权重分布

**SOP-3: 知识补充**

1. 每周扫描新会话
2. 提取技术决策/方案/模式
3. 建立与代码实体的关系
4. 同步到知识图谱

**理由**：

- 标准化流程，减少遗漏
- 定期执行，持续改进
- 可追踪、可审计

## Risks / Trade-offs

| 风险                 | 影响 | 缓解措施                         |
| -------------------- | ---- | -------------------------------- |
| 关键词匹配误报       | 中   | 语义相似度阈值过滤 + 人工审核    |
| 关系爆炸（过多关系） | 中   | 限制每个实体的最大关系数（20个） |
| 权重计算不准确       | 低   | 多维度加权 + 可手动调整          |
| 监控 overhead        | 低   | 异步记录 + 采样（10%）           |
| 人工审核瓶颈         | 中   | 优先级排序 + 批量处理            |

**Trade-offs**：

- **自动化 vs 准确性**：自动建立关系 + 人工审核关键关系
- **覆盖率 vs 精准度**：宁可少建关系，不建错误关系
- **实时性 vs 性能**：监控数据异步记录，不影响主流程

## Migration Plan

### Phase 1: 跨类型关系建立（1小时）

1. 提取新对话知识实体的关键词
2. 在代码实体中搜索匹配
3. 计算语义相似度
4. 建立applies_to/implements/related_to关系（目标50+个）
5. 计算并设置关系权重
6. 验证关系建立成功

### Phase 2: 补充对话知识（1小时）

1. 扫描历史会话（最近3个月）
2. 提取技术决策、方案、模式
3. 过滤已存在实体（去重）
4. 创建新实体（目标15-20个）
5. 建立与代码实体的关系
6. 同步到后端

### Phase 3: 质量监控机制（30分钟）

1. 实现搜索质量记录（latency, precision）
2. 实现关系健康度检查（孤立实体、平均关系数）
3. 实现每周报告生成
4. 配置自动化任务（每周一执行）

### Phase 4: 持续优化流程（30分钟）

1. 编写SOP文档
2. 实现孤立实体检测脚本
3. 实现关系权重优化脚本
4. 配置定时任务（每月1日执行）

### Phase 5: 验证和报告（30分钟）

1. 验证关系网络密度提升至0.02+
2. 验证关系网络评分提升至80+
3. 生成优化前后对比报告
4. 生成质量监控报告

### Rollback Strategy

- 备份现有关系数据
- 新关系标记为"auto-generated"便于识别和删除
- 可单独回滚各阶段优化
