## Context

当前质量监控和SOPs的问题：

1. **批处理模式**：每周/每月/每季度执行，无法及时发现开发过程中的问题
2. **被动等待**：开发者不知道何时该运行SOP，也不知道当前质量状态
3. **反馈延迟**：问题发现时可能已经积累了大量技术债务
4. **缺乏实时可见性**：没有实时仪表板查看知识图谱健康度

开发阶段需求：

- 编码时随时查看"现在知识图谱健康吗？"
- 发现孤立实体时立即修复，不等每月任务
- 提交代码前快速检查质量是否达标
- 实时看到质量指标变化趋势

## Goals / Non-Goals

**Goals:**

- 构建实时质量仪表板，显示当前知识图谱健康状态（< 1秒刷新）
- 实现即时SOP执行，支持单条SOP立即运行（< 30秒完成）
- 开发阶段质量守护，关键操作后自动轻量级检查
- 一键修复常见问题（孤立实体、低权重关系、缺失关联）
- 质量趋势可视化，显示最近7天变化

**Non-Goals:**

- 不替代周期性SOPs（仍保留每周/每月/每季度任务）
- 不实现复杂AI诊断（使用规则引擎）
- 不修改现有Entity-Atom架构
- 不增加后端负担（轻量级检查，本地优先）

## Decisions

### 决策 1：实时仪表板架构

**选择**：本地CLI工具 + 轻量级后端查询

**实现**：

```
opencode-memory quality-dashboard
├── 顶部：总体健康度评分 (0-100)
├── 左栏：实体统计 (总数、各类型分布)
├── 中栏：关系网络 (密度、孤立实体数、平均关系数)
├── 右栏：搜索质量 (最近10次查询延迟、准确率)
└── 底部：趋势图 (最近7天关键指标)
```

**刷新策略**：

- 手动刷新：按 'r' 键立即刷新
- 自动刷新：每60秒后台更新（可选）

**理由**：

- CLI工具开发成本低
- 本地计算减少后端压力
- 开发者习惯命令行工具

**替代方案**：

- Web仪表板：需要启动服务器，复杂度高
- IDE插件：需要适配不同IDE

### 决策 2：即时SOP执行引擎

**选择**：单条SOP独立执行，支持参数覆盖

**命令格式**：

```bash
# 执行完整SOP
opencode-memory sop run isolated-entities

# 执行SOP的特定步骤
opencode-memory sop run isolated-entities --step detect

# 带参数执行
opencode-memory sop run weight-optimization --threshold 0.6

# 预览模式（不实际执行）
opencode-memory sop run isolated-entities --dry-run
```

**SOP执行流程**：

1. 加载SOP定义（YAML格式）
2. 验证前置条件
3. 执行步骤（带进度显示）
4. 生成执行报告
5. 可选：自动修复或人工确认

**理由**：

- 灵活可控，支持部分执行
- 参数化配置适应不同场景
- 预览模式安全可控

### 决策 3：开发阶段质量守护

**选择**：Hook机制，关键操作后自动触发轻量级检查

**触发点**：

```javascript
// memory_write 后自动检查
memory_write({...}) → 触发质量检查
  → 检查是否产生孤立实体
  → 检查关系是否完整
  → 如有问题，显示警告和建议

// memory_relate 后自动检查
memory_relate({...}) → 触发质量检查
  → 检查权重是否合理
  → 检查关系类型是否正确
  → 如有问题，显示警告
```

**检查策略**：

- 轻量级：只检查相关实体，不扫描全图
- 异步：不阻塞主流程，后台执行
- 可配置：开发者可关闭自动检查

**配置示例**：

```json
{
  "quality_guard": {
    "enabled": true,
    "auto_check_on_write": true,
    "auto_check_on_relate": true,
    "threshold_isolated": 5,
    "show_warnings": true
  }
}
```

**理由**：

- 即时反馈，问题发现早
- 轻量级不影响性能
- 可配置适应不同需求

### 决策 4：一键修复策略

**选择**：规则引擎 + 自动修复 + 人工确认

**修复命令**：

```bash
# 诊断并显示问题
opencode-memory fix --dry-run

# 自动修复所有问题
opencode-memory fix --auto

# 交互式修复（逐个确认）
opencode-memory fix --interactive

# 修复特定类型问题
opencode-memory fix isolated-entities
opencode-memory fix low-weight-relations
opencode-memory fix missing-relations
```

**修复流程**：

1. 诊断阶段：扫描知识图谱，识别问题
2. 建议阶段：为每个问题生成修复建议
3. 执行阶段：根据模式自动或交互式修复
4. 验证阶段：修复后验证质量指标

**自动修复规则**：

- 孤立实体：自动建立到相关代码实体的关系（相似度>0.8）
- 低权重关系：重新计算权重
- 缺失关系：基于命名和语义匹配建议关系

**理由**：

- 减少人工操作
- 规则透明可控
- 交互模式安全

## Risks / Trade-offs

| 风险             | 影响 | 缓解措施                             |
| ---------------- | ---- | ------------------------------------ |
| 实时检查影响性能 | 中   | 轻量级检查 + 异步执行 + 可关闭       |
| 自动修复误操作   | 中   | 预览模式 + 交互模式 + 撤销支持       |
| 仪表板信息过载   | 低   | 可配置显示项 + 简洁模式              |
| 开发者忽略警告   | 中   | 分级警告（提示/警告/错误）+ 强制确认 |

**Trade-offs**：

- **实时性 vs 性能**：轻量级检查，可配置关闭
- **自动化 vs 安全性**：默认交互模式，可选自动模式
- **功能丰富 vs 简洁**：可配置显示项

## Open Questions

1. **性能阈值**：轻量级检查耗时应该<多少毫秒？（建议<100ms）
2. **警告分级**：什么情况下应该强制确认？（建议：孤立实体>10个）
3. **自动修复范围**：哪些修复可以自动执行？（建议：权重调整可以，关系建立需要确认）
4. **趋势数据存储**：7天趋势数据存储在哪里？（建议：本地JSON文件）
