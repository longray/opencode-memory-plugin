## Context

当前知识图谱存在严重覆盖率问题：

- **文件级覆盖**: lib/ 26个文件 → 1个实体（4%），tools/ 5个文件 → 1个实体（20%）
- **子目录遗漏**: websocket/ 6文件、precompute/ 3文件 0%覆盖
- **类级覆盖**: 4/19 类（21%），缺失 BM25Index、ProjectResolver、FileWatcher 等核心类
- **函数级覆盖**: 3/50+ 函数（6%），缺失 entry.js、extractor.js、indexer.js 等核心函数
- **工具覆盖**: 20个 Plugin Tools 0%覆盖

根本原因是 code-analyzer 未递归分析子目录，且粒度失衡（多文件合并为一个实体）。

## Goals / Non-Goals

**Goals:**

- 建立文件级扫描机制，使用 glob 遍历所有文件（包括子目录）
- 每个重要文件（>100行或有导出）创建独立实体，避免粒度失衡
- 实现 Module → Class → Function 三级递进构建
- 建立覆盖率验证机制，确保文件/类/函数三级覆盖率 >80%
- 补全 WebSocket、Precompute、Plugin Tools 等核心子系统
- 建立 contains/calls/depends_on 完整关系图谱

**Non-Goals:**

- 不修改现有 Entity-Atom 架构（保留 v3.3 设计）
- 不删除核心配置文件（AGENTS.md, SOUL.md 等）
- 不分析 node_modules 等第三方依赖
- 不实现实时自动分析（本次为一次性重建）

## Decisions

### 决策 1：文件级独立实体（避免合并）

**选择**：每个重要文件（>100行或有导出）创建独立 code_module/code_class 实体

**理由**：

- 避免 lib/ 26文件 → 1实体的粒度失衡问题
- 支持精准检索（搜索 bm25.js 直接找到 BM25Index 实体）
- 便于增量更新（单个文件变更只需更新对应实体）

**替代方案**：

- 目录级实体：过于粗糙，无法精准检索
- 函数级实体：过于细碎，实体数量爆炸

### 决策 2：递归 glob 扫描（不遗漏子目录）

**选择**：使用 `glob('lib/**/*.js')` 递归扫描所有子目录

**理由**：

- 确保 websocket/、precompute/ 等子目录不被遗漏
- 可配置排除模式（排除 node_modules, test/ 等）
- 与 code-analyzer --project 相比更可控

**替代方案**：

- code-analyzer --project：可能未递归子目录（导致当前问题）
- 手动列举文件：容易遗漏，维护困难

### 决策 3：三级递进构建策略

**选择**：Module → Class → Function 三级递进，每层验证后再进入下一层

**理由**：

- 避免一次性构建导致遗漏
- 每层可独立验证覆盖率
- 便于定位和修复问题

**流程**：

1. **Module 级**：扫描所有目录，创建 code_module 实体（目标：100%文件覆盖）
2. **Class 级**：分析每个文件，提取 class 定义（目标：>80%类覆盖）
3. **Function 级**：分析导出函数和关键内部函数（目标：>60%函数覆盖）

### 决策 4：覆盖率检查清单（防御性验证）

**选择**：建立文件/类/函数三级检查清单，每级构建后验证

**理由**：

- 防止遗漏成为隐性债务
- 量化覆盖率指标（文件100%/类80%/函数60%）
- 便于持续改进

**检查清单模板**：

```markdown
## Module 级检查清单

- [ ] lib/websocket/ 6个文件已分析
- [ ] lib/precompute/ 3个文件已分析
- [ ] tools/ 5个文件已分析
- [ ] 实际文件数：37，实体数：37，覆盖率：100%

## Class 级检查清单

- [ ] BM25Index 类已提取
- [ ] ProjectResolver 类已提取
- [ ] FileWatcher 类已提取
- [ ] 实际类数：19，实体数：16，覆盖率：84%

## Function 级检查清单

- [ ] entry.js 导出函数已提取
- [ ] extractor.js 导出函数已提取
- [ ] 实际导出函数：50+，实体数：35，覆盖率：70%
```

### 决策 5：关系图谱自动构建

**选择**：基于 import/export 和函数调用自动建立关系

**关系类型**：

- `contains`：模块包含类/函数
- `calls`：函数调用函数
- `depends_on`：模块依赖模块
- `implements`：类实现接口

**理由**：

- 自动提取比手动维护更可靠
- 支持图谱遍历（memory_graph）
- 便于理解代码架构

## Risks / Trade-offs

| 风险                   | 影响 | 缓解措施                               |
| ---------------------- | ---- | -------------------------------------- |
| 实体数量爆炸（>100个） | 中   | 设置阈值：>100行或有导出才创建实体     |
| 分析时间过长           | 中   | 分批次处理，每批次10个文件             |
| 关系提取不准确         | 低   | AST 分析优于正则匹配，关键关系人工校验 |
| 覆盖率目标未达成       | 中   | 三级递进验证，未达标不进入下一级       |
| 后端存储压力           | 低   | 40-50个实体在 SurrealDB 承受范围内     |

**Trade-offs**：

- **粒度 vs 数量**：选择文件级实体，平衡检索精准度和实体数量
- **自动化 vs 准确性**：AST 自动提取 + 关键关系人工校验
- **完整性 vs 时效性**：选择完整重建，牺牲时间换取覆盖率

## Migration Plan

### Phase 1: 准备与清理（20分钟）

1. 备份现有 14 个实体（可选）
2. 清空后端 SurrealDB/Meilisearch
3. 清空插件端 timeline 数据
4. 生成文件清单（glob 扫描）

### Phase 2: Module 级构建（30分钟）

1. 使用 glob 扫描 lib/, tools/, cli/, agents/
2. 为每个文件创建 code_module 实体
3. 验证：文件数 == 实体数（100%覆盖）

### Phase 3: Class 级构建（40分钟）

1. 对每个文件运行 code-analyzer
2. 提取 class 定义，创建 code_class 实体
3. 验证：类覆盖率 >80%

### Phase 4: Function 级构建（40分钟）

1. 提取导出函数和关键内部函数
2. 创建 code_function 实体
3. 验证：函数覆盖率 >60%

### Phase 5: 关系图谱构建（30分钟）

1. 分析 import/export 建立 depends_on 关系
2. 分析函数调用建立 calls 关系
3. 建立 contains 关系（模块→类→函数）

### Phase 6: 验证与报告（20分钟）

1. 生成覆盖率报告（文件/类/函数三级）
2. 测试搜索功能
3. 验证关系图谱完整性
4. 生成最终报告

### Rollback Strategy

- 清理前可选备份 timeline 目录
- 后端清空可通过重新上传恢复
- 分阶段验证，每阶段可独立回滚
