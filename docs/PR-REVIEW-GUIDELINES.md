# PR 审查规范

> **版本**: v1.0.0  
> **日期**: 2026-04-10  
> **适用范围**: v3.2 开发阶段

---

## 概述

本文档定义 v3.2 开发阶段的 PR 审查规范，确保每个 PR 都经过严格审查，实现符合设计文档。

---

## 审查流程

### 1. 自动化检查（CI）

PR 创建后自动运行：

| 检查项 | 工具 | 通过标准 |
|--------|------|----------|
| 代码风格 | `npm run lint` | 0 errors |
| Markdown格式 | `npm run lint:md` | 0 errors |
| 单元测试 | `npm test` | 100% pass |
| 代码覆盖率 | `npm run test:coverage` | ≥ 85% |
| 设计符合性 | 自定义脚本 | 通过 |

### 2. 人工审查

至少需要 **2 名审查者** 批准：

1. **技术审查者**（必须）：检查代码质量、设计符合性
2. **架构审查者**（必须）：检查架构符合性、性能影响

---

## 审查检查清单

### 2.1 设计符合性审查 ✅

**必须**检查代码是否符合设计文档：

- [ ] PR 包含 Design-Ref 引用
- [ ] 实现与设计文档一致
- [ ] API 契约符合设计规范
- [ ] 性能指标符合设计基准
- [ ] 错误处理符合设计规范

**审查方法**:
```bash
# 检查 Design-Ref
grep -r "Design-Ref" src/ --include="*.js" --include="*.py"

# 对比实现与设计文档
diff -u design.md implementation.md
```

---

### 2.2 代码质量审查 ✅

- [ ] 代码风格符合项目规范
- [ ] 无重复代码（DRY原则）
- [ ] 函数/类职责单一（SRP原则）
- [ ] 错误处理完整（try-catch、错误码）
- [ ] 日志记录适当（级别、内容）
- [ ] 注释清晰完整（JSDoc、docstring）
- [ ] 类型注解完整（TypeScript/Python）

---

### 2.3 测试覆盖审查 ✅

- [ ] 单元测试覆盖率 ≥ 85%
- [ ] 关键路径覆盖率 100%
- [ ] 集成测试覆盖主要流程
- [ ] 性能测试覆盖性能敏感点
- [ ] 测试用例包含边界条件
- [ ] 测试用例包含错误场景

**审查命令**:
```bash
# 检查覆盖率
npm run test:coverage

# 检查测试文件
find src -name "*.test.js" | wc -l
```

---

### 2.4 架构审查 ✅

- [ ] 模块依赖关系符合设计
- [ ] 无循环依赖
- [ ] 接口设计合理
- [ ] 数据流清晰
- [ ] 状态管理合理

**审查工具**:
```bash
# 检查依赖关系
dependency-cruiser src/

# 检查循环依赖
madge --circular src/
```

---

### 2.5 性能审查 ✅

- [ ] 无性能瓶颈（大O复杂度）
- [ ] 无内存泄漏风险
- [ ] 异步处理合理
- [ ] 缓存使用合理
- [ ] 数据库查询优化

---

### 2.6 安全审查 ✅

- [ ] 无硬编码密钥
- [ ] 输入验证完整
- [ ] SQL注入防护
- [ ] XSS防护
- [ ] 敏感信息脱敏

## 审查优先级

### 🔴 阻塞性问题（必须修复）

- 实现与设计文档严重不符
- 测试覆盖率 < 85%
- 存在安全漏洞
- 存在性能瓶颈
- 破坏向后兼容性（未声明）

### 🟡 建议修复（强烈建议）

- 代码风格问题
- 缺少注释
- 测试用例不完整
- 错误处理不完善

### 🟢 可选改进（可选）

- 代码优化建议
- 文档改进建议
- 重构建议

---

## 审查评论规范

### 评论格式

```
[级别] 模块: 问题描述

建议: 具体建议

参考: 相关文档/代码
```

**示例**:
```
[🔴 阻塞] websocket: 心跳间隔与设计不符

设计文档要求 30s，实现为 60s

建议: 修改为 30s，或更新设计文档

参考: BACKEND-v3.2-WEBSOCKET.md#3.1-心跳机制
```

### 评论级别

- **🔴 阻塞**: 必须修复，否则不批准
- **🟡 建议**: 强烈建议修复，但不阻塞
- **🟢 可选**: 可选改进，仅供参考

---

## 审查者职责

### 技术审查者

1. 检查代码质量
2. 检查设计符合性
3. 检查测试覆盖
4. 检查性能影响

### 架构审查者

1. 检查架构符合性
2. 检查模块依赖
3. 检查接口设计
4. 检查长期可维护性

|---------|----------|

| 中（100-500行） | 48小时内 |

## 审查记录

审查者必须在 PR 中留下审查记录：

```markdown
## 审查记录

**审查者**: @username  
**日期**: 2026-04-10  
**结果**: 批准 / 需要修改 / 拒绝

### 检查项

- [x] 设计符合性
- [x] 代码质量
- [x] 测试覆盖
- [x] 架构符合性

### 评论

1. [🔴 阻塞] xxx问题 - 已修复 ✅
2. [🟡 建议] xxx建议 - 可选

### 结论

批准合并 / 需要修改后重新审查
```

---

## 紧急修复流程

对于紧急修复，可以简化审查流程：

1. **创建 PR** 时标记 `[HOTFIX]`
2. **1 名审查者** 批准即可
3. **事后补充** 完整测试和文档

**要求**:
- 修复必须解决严重问题（崩溃、数据丢失）
- 修复必须在 24 小时内补充完整审查
- 修复必须记录在技术债务中
